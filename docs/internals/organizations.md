# Organization identity and authority

Organizations are independent of Projects. A Project continues to own its workspace and threads; an Organization owns its charter, role graph, configuration revisions, and explicit Project bindings. Creating or archiving either record does not create or delete the other. The current Project deletion path leaves a tombstone, so a binding retains its Project ID for audit while the deleted target is unavailable.

The first Organization store uses the server's existing SQLite connection and migration runner (`apps/server/src/persistence/Migrations.ts`). It lives in `apps/server/src/organizations/OrganizationStore.ts`, with wire schemas in `packages/contracts/src/organizations.ts`. It does not widen the existing Project/Thread event aggregate or place Organizations under `projection_projects`. Organization mutations commit their row changes and audit entry in one SQL transaction, compare the caller's draft revision, and reject a reused mutation ID. A partial unique index in migration 59 permits at most one active write binding per Project across all Organizations; read and proposal bindings remain possible.

The role graph describes responsibility and review relationships. Its edges do not grant tools or start work. Bindings carry explicit access and capabilities, and any future executor must check the current binding at dispatch time, including after a configuration was published. A role title, mandate, or graph edge cannot raise binding authority. Existing environment RPC scopes in `apps/server/src/auth/RpcAuthorization.ts` gate access to the Organization API, while the store enforces binding and revision rules. The WebSocket handlers in `apps/server/src/ws.ts` accept client governance mutations from browser sessions and locally bootstrapped desktop bearer sessions, then attribute them to the user. Generic bearer and relay sessions do not meet this gate. The handlers do not trust a client-supplied actor label. This is a narrow first-release boundary, not a general proof of physical human presence; a local administrator can issue credentials and development-mode reusable tokens have their own trust semantics.

Published configuration versions are immutable snapshots. Draft edits after publication do not rewrite the version already published. Activation remains unavailable until an Organization scheduler and executor enforce the published workflow, resource ceilings, and current binding permissions. Existing Agent Dashboard review and improvement loops are Project oriented and can later supply observations; they are not implicitly authorized to execute for an Organization.

Workflow definitions are stored separately from the responsibility graph and included in immutable published snapshots. Publication validates step roles, bounded cycles, independent QA, and routes to integration. A validated workflow definition is not running work. Migration 60 adds workflow JSON to existing Organization rows, and old published snapshots decode with an empty workflow list. Migration 61 adds intake sources, observations, tentative findings, and source governance audit.

The Designer includes a durable Architect conversation. Migration 64 stores request identities, messages, and restricted draft proposals; migration 65 repairs early development databases created before proposal positions and pending uniqueness were added. Configured, ready text providers can generate a structured turn from the Organization configuration, including bounded workflow context, and a bounded transcript. The six-stage prompt guides mission, roles, relationships, workflow, resources, and review. Provider adapters use temporary working directories and deny client tool/file/terminal requests for Architect turns; provider-owned hooks remain within the configured provider's trust boundary. The Architect cannot apply a proposal itself. The user applies one suggestion or an atomic batch from one response against the same draft revision. The batch validates the final graph and workflow definitions and commits one audit entry; an older draft revision fails. Duplicate request IDs never invoke the model again, and interrupted requests expire after 120 seconds, including on transcript refresh. Known credential patterns are redacted from stored conversation, proposal text, and outbound configuration. Identifier values containing credential-like text cause generation to fail before a provider call. Pattern-based redaction cannot identify every arbitrary secret, so the UI states which configuration and conversation fields will be sent. Adapter tests use fake providers; a live paid provider response has not been verified here.

The Workflows tab edits a saved definition as a revisioned draft. Its template contains trigger, work, independent QA, integration, and finish steps, with an optional bounded QA return. The editor performs quick local checks; publication remains the server validation boundary. Migration 62 adds pinned work items, attempts, leases, artifact references, approvals, recovery state, and idempotent transition records. The production `OrganizationWorkStoreLive` deliberately denies every work mutation. It provides read access to persisted state, but no provider-backed executor or dispatch authority is installed. Test-only policy injection exercises the transition rules without granting runtime authority.

The work-state policy seam receives the action, authenticated subject, Organization, Project, binding, scope, and work identity. New forward transitions require `active` lifecycle and recheck the current write binding. Pausing or archiving prevents additional dispatch, heartbeat, submission, QA, approval, and integration transitions; recovery and cancellation remain possible. These rules are tested with an injected execution authority. They do not imply the application can currently activate an Organization or stop a real subprocess.

Migration 70 adds durable attempt permits with global, Organization, and Project concurrency ceilings (defaults 4, 2, and 1). Claim and permit acquisition commit together; heartbeat renews the permit, and submit, cancellation, or explicit expired-attempt recovery releases it. An expired lease still occupies capacity until recovery, because a timeout alone cannot prove an old worker stopped writing. The migration preserves current running attempts as active permits. The production execution authority remains disabled. Any future executor must stop or isolate the old process before recovery makes a Project permit reusable, and it must separately enforce provider, CPU, memory, process, and usage budgets.

Migration 81 and `OrganizationProviderBudget` add a disconnected provider admission ledger. The seeded global limit is zero; a call needs explicit global, Organization, and Project capacity before it can reserve a bounded estimated-token allocation. SQLite serializes reservations and checks concurrent requests and daily call/token ceilings at all three scopes. A reservation has an immutable request identity; a single `markDispatched` transition must precede any provider call, and repeating it conflicts rather than authorizing a second dispatch. An expired reserved or dispatched lease becomes `uncertain` and continues consuming concurrency until an authorized reconciliation proves completion or non-dispatch. Recorded input/output tokens are measured values only when supplied; unknown usage stays labeled unknown, an actual usage overrun is preserved and stops further admission for that UTC day, and no monetary estimate is invented. Read-only totals distinguish active reservations, allocated estimates, measured tokens, unknown usage and overruns. Migration 83 adds a disconnected human-authorized configuration service with distinct host/global and scoped update policies, optimistic revisions, and an immutable audit of the actor and old/new ceilings. The service is not exposed through RPC or the UI, and the admission ledger is not wired to `TextGeneration`; no current runtime path authorizes provider spend.

`OrganizationWorkLaunchPlanner` is a read-only preflight for a future worker. It rejects work unless the Organization is active and published, the current Project binding still matches the pinned binding version and scope with repository capabilities, the pinned workflow exists, and the full Git commit resolves exactly. It returns deterministic attempt-specific worktree and branch names; it neither creates those resources nor grants execution. A future worker must repeat current-authority checks when claiming an attempt, since state can change after planning. `OrganizationSandboxHost` is a disconnected Linux host primitive. It uses a disposable capped tmpfs workspace, restricted read-only mounts, clear environment, no network, and a bounded stop fence over its pinned PID namespace; adversarial tests cover synthetic secrets, outside writes, disk exhaustion, and detached children. A mutable input staging race found in review was fixed by snapshotting caller values before the first await, and the exact escape reproduction was rechecked independently. Aggregate CPU, memory, and process limits remain unenforced by this primitive. `OrganizationSandboxProductionStatus.ready` remains false; no provider or work dispatch uses it.

`OrganizationScopedSandboxHost` adds an isolated candidate host path for Linux systems with a delegated systemd user manager and cgroup v2. It prepares a unique transient scope, verifies the exact invocation and kernel limits for memory, swap, process count, and aggregate CPU, and returns that identity while caller code is gated. An explicit start token is required; a closed pipe cannot launch caller code. Staged input is passed through unlinked file descriptors into read-only sandbox mounts, so a supervisor crash does not retain named input files. A systemd hard timeout is the requested runtime plus up to three seconds for preparation. Completion or cancellation must verify the exact scope and pinned PID namespace have no live processes. An unavailable user systemd manager fails closed.

Migration 71 adds a durable attempt-to-scope record with immutable unit, invocation, cgroup, PID, and PID namespace identity. `OrganizationWorkScopeStore` rechecks the current attempt, permit, lease, binding, and lifecycle when attaching and starting a scope. Its `startWithFence` holds an uninterruptible database write transaction until the trusted callback completes the FD4/FD5 token write; interruption cannot roll back the record while a write continues. The sandbox host awaits local stream completion for both pipes and destroys a stalled writable after three seconds, so its asynchronous `start()` can be used in that callback. Stream completion does not prove child consumption or successful execution. A disconnected test coordinator connects these parts with injected authorities; the production runtime does not mount it. Stop recording requires a verifier of the persisted OS identity, and its live default denies verification. WorkStore retains permits while an attached scope is unverified, rejects heartbeat after stop request, and accepts submission only after recorded start and verified stop plus a server-owned artifact check. The production runtime mounts the persisted artifact verifier but denies work mutation and artifact capture. Pause and archive reject running attempts or unverified scopes; Project detach also requires all bound work to be terminal. These guards preserve authority while execution remains disabled. A production worker, real OS stop verifier, provider routing, recovery orchestration, and immediate drain/emergency stop are still required.

Migration 72 stores one immutable artifact receipt per attempt. Its bounded patch and evidence bytes are hashed with a versioned, length-prefixed SHA-256 payload that includes the attempt, work, Project, base revision, exact scope identity, verified-stop time, and successful execution outcome. `OrganizationWorkArtifactStore` recomputes the digest from stored bytes before accepting a WorkStore submission target. `OrganizationPatchSandboxInput` is a disconnected payload builder for a single flat `.mjs` source replacement and selected `.mjs` smoke test. ## Configuration and authority decisions

1. **Separate identity:** Organization rows have no Project parent foreign key. Project bindings are independent durable records. Detachment preserves historical rows and audit entries.
2. **Typed responsibility graph:** A role edge describes responsibility. It grants no tool access. Layout coordinates live apart from semantic role and edge fields.
3. **Revisioned writes:** Each mutation has a unique ID and expected draft revision. One transaction applies the change and audit entry, or neither. Stale edits fail instead of replacing another editor's change.
4. **Published snapshot:** Publishing captures immutable configuration at a numbered revision. Subsequent draft edits leave it unchanged. Publishing is not activation.
5. **Current authority:** The live binding and server policy are the authority ceiling. A future executor must check both on each action, even when a run is pinned to an older published configuration. The database currently enforces one active write steward per Project.
6. **Execution seam:** A bounded observation-to-proposal scheduler runs for Organizations that opt in. No worker scheduler or executor is wired yet. The backend rejects activation rather than offering a state that looks live without work, leases, review, or recovery.

## Organization repositories

An Organization repository is intended to be a durable, collaborative record of the Organization, not a one-time role/workflow template. GitHub hosts one repository per Organization. The repository carries the charter and configuration history, role and workflow revisions, Architect and Director conversations, institutional memory and decisions, source descriptions and sanitized observations, findings and proposals, completed work and verification evidence, and Organization audit history. Records need stable IDs and schema versions so another user can clone or link the same repository, see the history, and contribute without replacing unrelated records. Git commits identify what was shared and when; per-record files let independent additions merge. Conflicting edits to the same record or configuration require an explicit resolution and must never silently choose the last push.

Local SQLite remains the runtime projection and execution authority. A linked repository records its remote identity, last accepted commit, and pending local changes. Save and sync must be repeatable: pull and validate remote changes, stage them for the Organization, then publish local changes with a compare-and-swap against the observed remote head. A failed push leaves local changes pending and visible. A new user loads the shared record into a local draft and maps Projects, source accounts, providers, and budgets in their own environment. Remote content can inform the Director and Architect as attributed knowledge, but it cannot grant project access, activate an Organization, approve work, set spend ceilings, or execute tools.

Credentials, source secrets, account tokens, absolute machine paths, live processes, leases, resource permits, and machine-specific Project binding authority never enter the repository. Source definitions and Project references may be shared as descriptive metadata; a recipient must reconnect them locally. Before first publication, the UI must show what will be shared, default to a private repository, and make the repo's visibility and sync state clear. Import must treat all repository files as untrusted data, validate size and schema, and keep imported policy changes as drafts until a local human publishes them. This boundary preserves the complete portable record of the Organization while avoiding a remote repo becoming an execution credential.

## Initial threat model

The Organization API accepts content from browser clients and will later accept external reports and model proposals. A client may claim to be a human, Architect, or Director; the WebSocket handler must derive the actor from the server session. A generic bearer token or delegated agent token cannot use the human governance path. A role prompt and graph edge cannot grant capabilities beyond an explicit Project binding. A publish operation must validate the full executable configuration and preserve its exact revision. External content is evidence to inspect, not a command to execute. A future executor must bind every side effect to current scope, policy, resource permits, approval, and reviewed artifact identity. These are required boundaries, not properties of the present Phase 1 implementation.

## Scope recovery and held permits

Migration 77 records `organization_work_scope_preparations` after a work attempt claims its durable permit and before the host may create a gated systemd scope. Migration 78 adds an immutable, unique unit-name reservation to that marker; migration 80 applies its final null-legacy-marker guard to development databases that already ran an earlier 78 revision. The disconnected attempt coordinator selects the unit name and commits it before calling the host. A reserved name identifies the scope to investigate after a crash between OS launch and scope attachment; the OS-assigned invocation and process identities are still recorded only after the host returns. Earlier unattached markers have no reserved name and remain ambiguous. If the host returns no scope identity, the preparation marker deliberately prevents lease recovery or cancellation from releasing that permit. This is an uncertain OS state, even if the lease has expired. The current production runtime cannot start these attempts; the condition is reproducible only with injected worker authorities.

For an isolated fixture, stop the worker process first and inspect the attempt, preparation marker, permit, and scope rows together. A row in `organization_work_scopes` with `verified_stopped_at` is the only current automatic release proof. When a marker exists without a scope row, inspect its reserved `unit_name` and the corresponding systemd user unit; legacy null reservations require a broader `t3-org-sandbox-*.scope` investigation. Inspect the worker process lifetime as well. Unit absence at one instant is not sufficient proof while a worker could still start preparation. Keep the permit held and the work in recovery until an authenticated recovery procedure can establish that no old worker can create or resume the scope and that any owned processes have exited. Do not delete the marker, edit the permit directly, or treat the lease timeout as cleanup. Fenced restart reconciliation remains required before live activation.

## Sources and safe demonstration

The Sources view can register a manual report source or a generic HTTP event source. Both are scoped to one Organization and may be restricted to a currently linked Project. A manual report arrives as an observation only; it does not create authorized work. The generic adapter issues a random source secret once at creation or rotation. The database stores its hash, source disable takes effect immediately, and the secret grants access only to the Organization intake HTTP routes. `POST /api/organizations/intake/events` accepts normalized events. `POST /api/organizations/intake/relay` accepts the strict GitHub issue and selected plain-text email relay formats, and requires a Project-bound source. Both routes accept up to 40 KiB of JSON, validate tighter event limits, and return only an outcome and observation ID. They never return stored observation text to a source-secret caller, including on duplicate delivery. They deduplicate on source event ID and key, redact recognizable credential patterns, and record no automatic actions. Keep the one-time secret in the sender's credential store, send it as an `Authorization: Bearer` header, and rotate or disable it from Sources if compromised. Registration, disable/enable, and rotation are audited. External content remains untrusted evidence.

Each source accepts at most 1,000 new observations in a sliding hour measured by server receipt time. Duplicate deliveries return a minimal duplicate receipt without consuming that quota; excess new events receive HTTP 429 with `Retry-After: 3600`. Archive stops intake and source re-enablement. This first limit is per source. The Sources view derives last intake and correlation backlog/error indicators from saved rows; direct connector health, Organization-wide quotas, retention, and pagination of observation history are still needed before sustained high-volume use.

After authenticated manual or HTTP intake saves an observation, a server-owned correlation pass reads only its persisted `attributes.correlationKey`. It groups observations from at least two distinct registered sources only when their exact Organization, Project, and key match, their sources remain enabled, and the Project remains bound. Two relays of the same upstream GitHub issue or email message count as one provenance identity. Projectless, disabled-source, or changed evidence is marked skipped or ambiguous. A tentative finding records each observation's source and Project. Migration 67 atomically queues correlation with each new observation and backfills older observations. A server-owned loop claims up to 32 due jobs per pass, recovers expired leases, backs off transient errors, and stops after eight failed attempts; immediate success settles the queued job. The Sources view shows pending, checking, complete, and terminal status, and an interactive user can retry a saved observation. Duplicate adapter delivery does not rerun correlation. A tentative finding does not authorize work or assert causation. No body-text similarity, cross-Project routing guess, or automatic worker dispatch is performed.

Migration 68 adds an explicit observation mode and a separate proposal queue. An interactive user enables it in Governance after publishing a configuration. Enabling sets a fresh epoch; findings created before that epoch or while mode was off are not imported. Every five seconds the server scans at most 32 due candidates, with an eight-candidate ceiling per Organization. It requires a current scoped finding, enabled evidence sources, an active proposal or write binding, and `propose-work` in both the current binding and published snapshot. A saved proposal pins the finding, evidence, binding version, and published revision. Its title and summary are bounded and pattern-redacted. The list pages through at most 100 records and derives current eligibility; stale proposals cannot be acknowledged. Human acknowledgement, rejection, or deferral is versioned, idempotent by mutation ID, and records a bounded/redacted reason. These decisions do not create work. Pausing, archiving, or disabling observation mode stops new proposal reconciliation; existing records remain visible for audit.

Migration 82 adds immutable waiting work intents. A server-owned five-second loop takes at most 16 newest and 16 fair older proposals per pass, excluding proposal versions already represented by an intent. Within a SQLite write transaction, each new intent checks the proposal state/version, opt-in epoch, tentative finding, enabled source evidence, nondeleted Project, current binding and published binding snapshot. It records the system actor, evidence, binding version and published revision. Reads derive whether a saved intent is now stale and page at 100. A waiting intent is not an approved or executable work item: it has no selected workflow/mandate, pinned code revision, worker, provider allocation, or integration target. The lifecycle activation and WorkStore mutation gates remain closed. Live Operations shows the first page of waiting intents through a read-only Organization-scoped RPC, labeling current and stale records without implying execution. Its direct human creation entry point is not exposed; if added, it must receive a principal constructed at an authenticated server boundary.

Migration 66 adds Organization memory and decision records with explicit Organization or Project scope, provenance, review and retention dates, and append-only revision snapshots. Interactive users can create, correct, supersede, and archive records through server-enforced mutation IDs and version checks. Changes require an active Project binding; historical Project records remain readable after detachment or Organization archive. The workspace pages through records and revisions in groups of 100. Retention and staleness dates are labels; automated erasure and revalidation before action remain future work. No model may write memory through the current API.

Migration 69 adds a separate, persisted Director conversation. An interactive user may ask about the Organization or a currently linked Project. Each request ID binds the actor, Organization, scope, and exact question; a replay reads its original answer without generating again. The current Director reply is a deterministic snapshot of at most six saved records per evidence category, with typed observation, tentative finding, open proposal, and verified work references. Organization-wide questions include currently bound Projects; scoped questions stay within their selected Project. No raw observation or finding body enters a reply. The response states when work is unverified, execution is unavailable, and cost is unknown. This is a status-report capability, not a model-driven diagnosis or autonomous coordinator. Transcripts are separately paginated by scope, and historical scoped messages remain readable under Organization audit access after detachment; new scoped questions require a current binding.

```json
  "sourceId": "<source ID>",
```


The email variant uses `kind: "plain-text-email-relay"`, `relayEventId`, an RFC Message-ID, `selectionReason` (`bug-report`, `incident-alert`, or `support-escalation`), optional `correlationKey`, `subject`, and `plainText` in place of the issue fields. Exact top-level fields, bounded plain text, and an explicit RFC3339 timestamp are required; raw headers, HTML, and attachments are rejected. Upstream account authentication and relevance selection remain the relay operator's responsibility. These formats were tested with fixtures, not a live GitHub or mailbox integration.

This describes a publishable workflow graph and fixture test path, not an active dispatcher. The current designer does not configure provider selection or execution budgets, so do not attach a real provider or grant live write authority for this demonstration. Publish validates the draft and records an immutable version; it does not dispatch a worker or integrate code.

No live issue tracker or email connector was accessed. Native provider connection, full source health/lag telemetry, live workflow execution, a browser-verified approval journey with saved artifact, and model-driven Director investigation remain pending. Cross-source correlation has fixture-level validation through authenticated generic and relay payloads and a server policy that creates tentative findings.
